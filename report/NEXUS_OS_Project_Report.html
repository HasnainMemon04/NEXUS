CS-2006 Operating Systems — Project Report NEXUS Task Orchestration Engine

Abstract

This report documents the design, implementation, and empirical evaluation of NEXUS, a multithreaded task orchestration engine developed in C11 on FreeRTOS (ESP-IDF v6.1) for CS-2006 Operating Systems (Project #2: Cloud Task Orchestration Engine). The system runs across an offline four-board cluster comprising one dual-core ESP32-S3-N16R8 master coordinator and three dual-core ESP32-D0WD-V3 worker nodes, providing eight active CPU cores with no external router, cloud service, or Python runtime.

Every board reuses a shared node engine implementing core operating system primitives: a bounded producer-consumer job queue guarded by a mutex and two counting semaphores, a fixed pool of four reusable executor threads regulated by a live-adjustable counting-semaphore permit cap (K = 1..4), non-blocking asynchronous logging, and sampled FreeRTOS task monitoring. Across boards, the master schedules jobs using six configurable (ordering, placement) policy pairs—combining FCFS, strict priority, and priority with aging against round-robin and capacity-aware least-loaded placement—and exchanges framed binary messages over a local Wi-Fi SoftAP.

Fault tolerance relies on 500 ms worker heartbeats, 3.0 s failure detection, per-job leases, cooperative execution-budget cancellation, and at-least-once dispatch with exactly-once commit semantics. A single-page operator dashboard gzipped into the master's flash (21,959 bytes) streams live telemetry over WebSockets and visualizes distributed Mandelbrot fractal rendering alongside interactive synchronization laboratories. Over a live 22-minute cluster run, NEXUS committed more than 46,692 jobs with zero failures, balanced 150-tile frames evenly across Workers A, B, and C (52 / 51 / 47), demonstrated 15.9× priority-inversion latency reduction via mutex priority inheritance on physical hardware (320 ms vs. 20.1 ms), detected worker failure in 3,024 ms with automatic job requeuing, and achieved up to 2.24× remote makespan speedup scaling from one to three workers on 32×32 matrix workloads while quantifying Amdahl's Law communication limits against local shared-memory execution.

CS-2006 Operating Systems — Project Report 1. Introduction & Project Objectives

1.Introduction & Project Objectives

1.1 Motivation & Operating Systems Focus

Modern cloud orchestrators coordinate concurrent job streams across shared pools of execution threads while enforcing fairness, resource bounds, and failure recovery. Although production platforms hide these mechanics beneath layers of virtualization and managed runtimes, their correctness depends directly on foundational operating system primitives: mutual exclusion, bounded-buffer synchronization, counting semaphores, priority scheduling with aging, deadlock avoidance, and message-passing interprocess communication (IPC).

NEXUS implements Project #2 (Cloud Task Orchestration Engine) strictly as an operating systems engineering project in C11 on FreeRTOS (ESP-IDF v6.1). An early proposal variant that included a cybersecurity analytics layer was intentionally discarded before implementation so that 100% of firmware complexity, testing, and evaluation targets OS mechanisms rather than application logic. Workloads are deterministic, parameter-seeded compute kernels—primarily a 600×400 Mandelbrot fractal divided into 150 independent 40×40 pixel tiles—so that every scheduling priority, load-balancing decision, semaphore cap, and node failure becomes directly observable and checksum-verifiable.

Architectural Boundary (Threads vs. Processes): Within each ESP32 board, FreeRTOS tasks operate as kernel-scheduled threads sharing a single physical address space and coordinating via mutexes, semaphores, and spinlocks. Across the four separate boards, nodes occupy isolated physical memories and exchange fixed binary frames over a local TCP link—directly demonstrating message passing between separate address spaces (Silberschatz OSC 10e §3.4). Moreover, an authoritative Single-Node Mode executes the entire engine locally on the master board with zero network involvement, confirming that the network serves strictly as a message transport rather than the subject of the project.

Why Four Boards (8 Cores)?

  • Isolated Failure Domains: Unplugging or rebooting one worker leaves the remaining nodes operational, enabling true crash detection and task migration.
  • Shared Memory vs. Message Passing: Contrasts intra-board SMP threads (shared RAM) with inter-board nodes (private address spaces communicating via framed messages).
  • Non-Trivial Placement & Scaling: Round-robin and least-loaded policies diverge only with multiple targets, and three workers allow 0/1/2/3-node scaling curves in Suite T5.
  • Heterogeneous RAM Fit: Master holds the 600×400 framebuffer and 4,096-job history in 8 MB PSRAM, while workers operate cleanly inside classic ESP32 internal SRAM.

3.Firmware Design, Task Hierarchy & Memory Layout

3.1 Modular Firmware Organization

The codebase under firmware/ separates shared OS mechanisms from board roles across three ESP-IDF components:

  • components/nexus_core/ (Shared Node Engine): Implements job_queue.c (bounded priority buffer and master in-flight tracker), exec_pool.c (fixed 4-thread pool and semaphore permit cap), kernels.c (Mandelbrot, matrix multiplication, spin), proto.c (framed TCP), logger.c, monitor.c, and oslab.c (Labs A–D), configured centrally in nexus_config.h.
  • master/main/ (Coordinator): Hosts the 20 MHz NEXUS-OS SoftAP (wifi_ap.c), cluster node table, dispatcher, and supervisor (cluster.c, placement.h), workload producers (producers.c), 4,096-job stats ring (stats.c), benchmark suites T1–T5 (experiments.c), and the HTTP/WebSocket dashboard (web.c, www/index.html).
  • worker/main/ (Worker): Connects as a Wi-Fi STA with WIFI_PS_NONE (wifi_sta.c) to avoid ~100 ms DTIM wake latency, discovers the master via DHCP gateway, and runs link_rx / link_tx feeding a local 8-slot queue and 4-executor pool (worker_link.c).

CS-2006 Operating Systems — Project Report 4. Concurrency, Synchronization & Deadlock Prevention

4.Concurrency, Synchronization & Deadlock Prevention

4.1 Bounded-Buffer Job Queue & Fixed Executor Pool

The core synchronization structure in job_queue.c implements the classical bounded-buffer producer-consumer pattern (OSC 10e §7.1.1) extended for priority selection and atomic in-flight state tracking. Rather than using a FIFO-only FreeRTOS queue, NEXUS protects an array of waiting jobs (ready[256]) and the master's active tracking table (inflight[32]) under a single mutex (q_mtx), paired with two counting semaphores: sem_free (initialized to capacity) and sem_ready (initialized to 0). Producers call jq_submit(), which acquires sem_free, locks q_mtx, inserts the job, unlocks, and posts sem_ready. Consumers split acquisition into jq_wait_ready() followed by jq_pop_best() so that executor threads can acquire an execution permit between waking and removing a job.

In exec_pool.c, pool_start() creates N = 4 permanent executor threads at boot (avoiding per-job task creation overhead, OSC 10e §4.5.1). Concurrency is throttled independently by a counting semaphore sem_slots holding K ≤ N permits (default K = 2 to match each board's two CPU cores, live-adjustable 1..4). Raising K posts additional permits immediately; lowering K never preempts an active job—instead, idle permits are drained immediately and active surplus permits are retired gracefully inside return_permit() upon job completion.

4.2 Synchronization Inventory & Deadlock Prevention Proof

Deadlock requires mutual exclusion, hold and wait, no preemption, and circular wait (OSC 10e §8.2). NEXUS eliminates circular wait structurally through an acyclic lock hierarchy across all synchronization objects (Table 5):

  • No Simultaneous Subsystem Locks: The four subsystem mutexes (q_mtx, nodes_mtx, frame s_fmtx, and stats s_mtx) are never held concurrently; each module locks, copies required fields to stack variables, and unlocks before calling another module.
  • Fixed Blocking Order: Blocking waits obey the strict partial order sem_free / sem_ready → sem_slots → q_mtx. When supervisor_task requeues jobs under q_mtx, it calls xSemaphoreTake(sem_free, 0) non-blockingly and defers full-buffer retries via requeue_pending on the next 100 ms tick.
  • Leaf Spinlocks & Outer View Lock: The pool's portMUX spinlock protects only short non-blocking counter updates, and web.c's JSON build mutex is always strictly outermost. Because the wait-for graph is acyclic, deadlock is impossible by construction.

CS-2006 Operating Systems — Project Report 5. Two-Level Scheduling, Placement & Compute Workloads

5.Two-Level Scheduling, Placement & Compute Workloads

5.1 Level-1 Distributed Job Scheduling vs. Level-2 SMP Kernel Scheduling

Scheduling in NEXUS operates at two distinct layers. At Level 1 (Orchestration), the master's dispatcher_task selects which queued job runs next and which board executes it using a configurable (ordering, placement) policy pair. At Level 2 (Operating System Kernel), FreeRTOS on each ESP32 board schedules its ready tasks across Core 0 and Core 1 using preemptive priority scheduling with 10 ms round-robin time-slicing among equal-priority executors. When a worker's permit cap K exceeds its two physical cores (K = 3 or 4), the dashboard visually hatches the third and fourth active slots (as seen in Figure 3) to distinguish true hardware parallelism from kernel time-slicing.

Queue Ordering Policies (jq_effective_priority)

  • FCFS: Assigns effective priority 0 to every job so the earliest monotonic sequence number always dispatches first.
  • Strict Priority: Selects the highest base priority (P3 down to P0), breaking ties by sequence number. Under continuous high-priority arrivals, P0 jobs experience classic starvation.
  • Priority + Aging (OSC 10e §5.3.4): Computes eff = min(3, base + ⌊wait_ms / 1500⌋). Every 1.5 s spent waiting boosts effective priority by one level, guaranteeing bounded wait times for P0 jobs even during a P3 storm. Requeued jobs preserve their original sequence number and submit timestamp so failures never push them to the back.

Node Placement & Prefetch Credits (choose_node)

  • Credit Flow Control: A node is eligible only if it is ONLINE, not draining, and holds fewer than K + 1 in-flight jobs. The extra +1 credit prefetches one job to hide Wi-Fi round-trip latency while strictly capping blast radius: a crashed worker loses at most K + 1 jobs.
  • Round-Robin: Rotates across eligible nodes in cyclic order regardless of remaining job cost.
  • Capacity-Aware Least-Loaded: Picks the eligible node minimizing in_flight / K, naturally steering new tiles toward boards that finished faster-escaping outer fractal tiles.

5.2 Deterministic Parameter-Seeded Workloads

Every job message (nx_job_spec_t, exactly 32 packed bytes) carries only parameters and seeds rather than bulk input arrays, keeping dispatch frames tiny. Three kernels run inside kernels.c: (1) Mandelbrot Fractal (NX_JOB_FRACTAL), splitting a 600×400 canvas into 150 uneven-cost 40×40 pixel tiles prioritized from center (P3) to corners (P0) using single-precision hardware FPU arithmetic; (2) Seeded Integer Matrix Multiplication (NX_JOB_MATMUL, n × n up to 32×32 generated via xorshift, outputting a CRC32 digest); and (3) Timed Spin (NX_JOB_SPIN) for controlled starvation and runaway-timeout testing. Every kernel polls esp_timer_get_time() against deadline_us and cooperates cleanly by returning NX_RES_TIMEOUT on expiry, because abruptly deleting a FreeRTOS task risks leaking locks or scratch state.

CS-2006 Operating Systems — Project Report 6. Message-Passing IPC & Fault Recovery Model

6.Message-Passing IPC & Fault Recovery Model

6.1 Framed Binary Protocol & Single-Writer Socket Discipline

Because TCP presents an unstructured byte stream, NEXUS encapsulates every inter-board message in an explicit binary frame defined in proto.h and validated with C11 _Static_assert layout checks. Each frame begins with an 8-byte packed header: magic = 0x584E ("NX"), version = 1, type (HELLO, WELCOME, DISPATCH, ACK, RESULT, HEARTBEAT, or CONTROL), 16-bit payload length (up to 2,048 bytes for a 1,600-byte Mandelbrot tile result), and 2 reserved bytes. On the receiving side, nx_recv_frame() loops until exactly 8 header bytes arrive, verifies magic/version/bounds, and reads the exact payload length regardless of TCP segmentation. Partial or malformed frames immediately close the stream with distinct diagnostics (EOF vs. EBADMSG vs. socket error).

To prevent concurrent tasks from interleaving bytes on a shared socket without locking the network stack, every TCP link uses a single-writer architecture: only one dedicated link_tx task ever invokes send() on a socket. All producers of outbound traffic—the dispatcher, control handlers, admit(), or worker executors—enqueue messages onto that link's bounded FreeRTOS tx_queue. On workers, link_tx simply waits on tx_queue with a 500 ms timeout; whenever no result or ACK is pending, the timeout itself triggers a HEARTBEAT packet, avoiding an extra task and keeping the single-writer invariant intact.

6.2 Worker Identity, Heartbeat Detection & Lease Semantics

Physical Wi-Fi disconnects cannot be relied upon for timely crash detection: a board whose USB cable is pulled transmits no TCP FIN, and ESP-IDF's SoftAP inactivity timer does not deauthenticate a silent station for 300 seconds by default. NEXUS therefore combines three complementary mechanisms:

  • MAC + Incarnation Identity: Upon booting, each worker generates a random 32-bit incarnation token and sends it alongside its 6-byte factory MAC in HELLO. If a board reconnects with the same MAC and the same incarnation (transient Wi-Fi glitch), in-flight work may still complete. If the incarnation changed (crash/reboot), the master immediately requeues all prior jobs assigned to that node.
  • Heartbeat Supervisor (supervisor_task, 100 ms tick): Workers send heartbeats every 500 ms carrying active job IDs, slot counts, core loads, sampled tasks, and an optional 10-byte extended trailer confirming chip type, core count, and SET_SLOTS generation acknowledgements. Silence exceeding 1.5 s transitions the node to SUSPECT; silence reaching 3.0 s declares it OFFLINE and triggers jq_requeue_node().
  • Per-Job Leases & Exactly-Once Commit: Every dispatched job carries a master-side lease equal to budget_ms + 2000 ms. Even if a worker stays alive and sends heartbeats, a lost dispatch or stalled job triggers lease expiry and requeuing (up to NX_MAX_ATTEMPTS = 3). NEXUS provides at-least-once execution coupled with exactly-once commit: inside jq_commit(), the first valid result for a job_id commits its pixels/statistics and cancels any requeued copy, while any delayed duplicate from a muted or recovered worker increments the duplicate counter and is safely discarded.

CS-2006 Operating Systems — Project Report 7. Synchronization Laboratory & Fault Injection Results

7.Synchronization Laboratory & Fault Injection Results

7.1 On-Hardware Verification of Classic OS Concurrency Phenomena

To make low-level concurrency bugs and their kernel remedies directly reproducible on demand, oslab.c embeds four controlled experiments executable on any board from the Control Center. Figure 7 shows a live run executed on physical Worker A (ESP32-D0WD-V3, dual-core 240 MHz) alongside the Fault Injection & Recovery panel:

  • Lab A (Lost-Update Race Condition): Two tasks pinned to Core 0 and Core 1 each execute a non-atomic read-modify-write increment 100,000 times on a shared 32-bit counter without locking. Due to true parallel execution across both Xtensa cores, simultaneous reads overwrite updates: Worker A finished at 103,185 instead of 200,000—losing 96,815 updates (48.4%) in 7.7 ms.
  • Lab B (Mutex Protection & Cost): Wrapping the identical increment inside a FreeRTOS mutex restored exact correctness (200,000 / 200,000, zero lost updates), while increasing runtime to 2,890 ms—directly quantifying the cost of fine-grained lock contention across two cores.
  • Lab C (Counting Semaphore Permit Cap): Six competing tasks execute 10 jobs each (60 jobs total) gated by a counting semaphore with 2 permits. Worker A completed all 60 jobs with a verified peak concurrency of 2 / 2, never violating the permit invariant.
  • Lab D (Priority Inversion & Inheritance, OSC 10e §6.8.2): Low (L), Medium (M), and High (H) priority tasks are pinned to Core 1 (with lab_run isolated on Core 0). L acquires a lock for 20 ms of work, H blocks on the lock, and CPU-bound M runs for 300 ms. With a binary semaphore (no priority inheritance), M preempts L and delays H for 320 ms. Switching to a FreeRTOS mutex lets L temporarily inherit H's priority, finish immediately without preemption by M, and drop H's wait to 20.1 ms—a 15.9× latency reduction.

8.NEXUS Control Center & Live Cluster Operation

8.1 Embedded Offline Dashboard Architecture

Project #2 specifies a GUI dashboard displaying queued, running, and completed tasks. Because the cluster operates on an isolated SoftAP with no internet connectivity, the entire operator console (firmware/master/main/www/index.html) is written in dependency-free HTML, CSS, and JavaScript, gzipped at build time to 21,959 bytes, and linked directly into the master's read-only flash partition. Opening http://192.168.4.1/ from any laptop or phone attached to NEXUS-OS loads the interface in a single HTTP response.

Live updates flow over a persistent WebSocket endpoint (/ws) driven by telemetry_task at an adaptive rate: up to 4 Hz while jobs are executing and 2 Hz when idle, with at most one queued broadcast frame to prevent back-pressure on the HTTP server. Completed Mandelbrot tiles are fetched in paginated batches of eight via a monotonic version watermark (/api/tiles?since=N) through a fixed 12,840-byte response buffer, eliminating large heap spikes. During integration on ESP-IDF v6.1, we resolved a subtle server change where ESP-IDF completes WebSocket handshakes without invoking the URI handler on HTTP_GET; ws_broadcast() now enumerates active file descriptors dynamically via httpd_get_client_list() and httpd_ws_get_fd_info().

9.2 Controlled Hardware Benchmark Protocol (experiments.c)

For repeatable physical measurements, the master firmware embeds a dedicated experiment runner (experiments.c) supporting five structured suites: T1 Scheduling (all 6 ordering × placement pairs on a mixed-priority workload), T2 Correctness (single-node CRC vs. distributed 4-producer burst of 310 commits), T3 Recovery (Worker A crash at 40% frame completion), T4 Slots (sweeping K = 1..4 across Workers A, B, and C with correlated ACKs), and T5 Scaling (comparing 0, 1, 2, and 3 workers on 100 seeded MATMUL jobs at n = 12 and n = 32, repeated three times per configuration).

To prevent measurement contamination, starting a suite pauses background client tasks and auto-zoom, locks out manual dashboard controls, waits for three consecutive idle checks, tags all commits with a run ID, and measures all latencies exclusively on the master's microsecond clock (esp_timer_get_time()) so inter-board clock skew never affects results. Summaries export via /api/runs.csv and raw job records via /api/csv.

11.1 Multi-Worker Load Balance & Mandelbrot Render Progression

Unlike uniform matrix kernels, Mandelbrot tiles vary sharply in compute cost: boundary tiles near the fractal cardioid execute up to max_iter floating-point iterations per pixel, while exterior tiles escape in fewer than 10 iterations. Under capacity-aware least-loaded placement with K + 1 prefetch credits, workers that draw cheap exterior tiles return credits quickly and absorb additional tiles automatically. Across both irregular fractal frames (Frame 265: A 52 / B 51 / C 47) and uniform T5 batches (n=32 3-worker runs: A 34 / B 34 / C 32 and A 35 / B 35 / C 30), deviation from an ideal 33.3% split stayed within ±2.5%.

12.Limitations, Engineering Lessons & Conclusion

12.1 Stated Architectural Limitations

An accurate systems evaluation must state its boundaries clearly alongside its achievements:

  • Master Single Point of Failure: NEXUS tolerates any combination of worker crashes, but the master coordinator itself is not replicated. Surviving master failure would require state-machine replication and leader election (OSC 10e §19.5), which lies outside the scope of CS-2006 Project #2.
  • At-Least-Once Execution Semantics: If a worker experiences a transient network pause exceeding the 3.0 s heartbeat threshold, its jobs are requeued and may execute a second time elsewhere before the delayed result arrives. Exactly-once guarantees apply strictly to the commit point (jq_commit), which is sound for idempotent deterministic workloads.
  • Sampled Monitor vs. Exact Scheduler Trace: The FreeRTOS task table samples uxTaskGetSystemState() every 500 ms rather than recording every microsecond context switch (which requires JTAG trace hardware such as Segger SystemView).
  • Kernel Granularity & Radio Contention: As demonstrated in Suite T5, distributing sub-millisecond workloads (MATMUL n=12) over 2.4 GHz Wi-Fi incurs higher IPC latency than local shared-memory execution; distributed speedup materializes only when per-job computation outweighs message-passing overhead.
  • Lab-Scope Transport Security: The dashboard serves plain HTTP/WebSocket over a WPA2-protected local SoftAP, which is appropriate for an isolated lab cluster but would require TLS and client authentication in an untrusted network.

12.2 Key Engineering Lessons Learned

Building a real-time multithreaded orchestrator on resource-constrained dual-core microcontrollers surfaced practical kernel behaviors that desktop simulations often obscure:

  • Task Watchdog & Idle Starvation: Two CPU-bound executors pinned across Core 0 and Core 1 can completely starve both FreeRTOS IDLE tasks and trip ESP-IDF's 5-second Task Watchdog. Inserting a single-tick yield (vTaskDelay(1)) at least once per second inside the executor loop preserved full throughput while keeping watchdog health clean.
  • Wi-Fi Power-Save & Bandwidth Tuning: Leaving ESP-IDF's default STA modem-sleep enabled adds up to 100 ms of beacon-interval latency per dispatch. Explicitly disabling power save (WIFI_PS_NONE) and pinning the SoftAP to 20 MHz bandwidth with TCP keepalives stabilized multi-worker links during long-running sessions.
  • ESP-IDF v6.1 WebSocket Discovery: Discovering active WebSocket file descriptors via httpd_get_client_list() rather than relying on an initial HTTP_GET handler invocation fixed silent telemetry drops during idle connections.

12.3 Conclusion

NEXUS fulfills all mandatory and extended requirements of CS-2006 Project #2 through a clean, self-contained C11 and FreeRTOS implementation running across eight physical CPU cores on four ESP32 boards. By pairing a shared bounded-buffer node engine with two-level scheduling, acyclic deadlock-free locking, framed message passing, heartbeat/lease fault recovery, and an offline interactive Control Center, the project makes core operating system principles directly observable and quantitatively verifiable. Live hardware sessions exceeding 46,692 committed jobs, 15.9× priority-inversion latency reduction on Worker A, 3.024 s failure detection with automatic requeuing, and 2.24× remote worker scaling on 32×32 matrix workloads confirm both functional correctness and predictable real-time performance.
